## Task 2: Create Supabase schema migrations for `applications`, `application_uploads`, Storage bucket `application-uploads`, policies

**Priority: high**  
**Depends on: Task 1 (only for secrets needed in `drizzle.config.ts` optional; migrations themselves can be written first)**

### Work items

1. Create a new SQL migration under `supabase/migrations/0001_create_applications.sql` (or within `drizzle/migrations/` if continuing the existing pattern). File must be idempotent (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, or use `supabase db diff` output) containing:
   - `applications` table per FR-2.1 with all required columns, PK, FK to `auth.users`, 5 `jsonb` fields (personal, banking, business, id_verify, kaccess), app_id_short unique, status, ip, user_agent, visitor_session, timestamps.
   - `application_uploads` table with FK cascade, `storage_object_path` not null, mime type, size, original filename.
   - Apply `updated_at` trigger on `applications` (reuse `public.set_updated_at` function which exists from 0000 migration; create if missing).
   - Indexes: `(created_at DESC)`, `(user_id)`, `(application_uploads.application_id)`, `(app_id_short UNIQUE)`.
   - RLS enable on both tables.
   - RLS policies per FR-2.2: authenticated self-select + self-insert for applications and linked uploads. DELETE/ALL across both only through service role (no user policy for deletion).
2. Create a second migration or inline in the same script a `sql/0001b_storage.sql` equivalent (Supabase Storage `buckets` table lives in `storage` schema):
   - Insert `INSERT INTO storage.buckets (id, name, public) VALUES ('application-uploads', 'application-uploads', false) ON CONFLICT DO NOTHING;`

     - Users may upload only to bucket='application-uploads' AND path prefix is `(auth.uid()::text || '/')`
     - Users may SELECT their own objects (path prefix match)
     - Admin reads use signed URLs generated server-side via service role, so we don't need a public-read policy
3. Extend `src/integrations/supabase/types.ts` `Database.public.Tables` declaration with `applications` and `application_uploads` types to match the new schema. Add/update the types file to prevent TS errors if any file imports `client.ts`.
4. Provide a `supabase/apply-migrations.ps1` (and `.sh`) shell script that takes the Supabase DB URL from `.env` and runs the migration SQLs in order, either via `psql` or the Supabase CLI (`supabase db push`). Document usage for each.

## Task 3: Backend API layer (Express server) that serves static site + exposes `/api/*`

**Priority: high**  
**Depends on: Task 1, Task 2**

Per Constraint C3 we choose **Option B (Express/Node)** because it runs locally with zero additional Supabase setup, serves static HTML + JSON API on one port, and integrates directly with `dotenv` for secrets. Option A (Edge Functions) is deferred as an alternate path documented in the spec.

### Work items

1. Create `server/index.js` as a new Express app using:
   - `dotenv` for `.env` load
   - `express` for HTTP
   - `@supabase/supabase-js` for service-role Supabase client + standard publishable client
   - `multer` for multipart file parsing (in case we also accept file uploads via HTTP multipart as a fallback)
   - `cookie-parser` for admin sessions
   - Built-in Express static middleware for serving everything under the repo root (`index.html`, `application.html`, `/js`, `/css`, `/images`, `svg`, favicon, etc.)
2. Implement endpoints:
   - `GET /health` → `{ ok: true }`
   - `POST /api/submit-application` → [see Task 4 details]
   - `POST /api/telegram-proxy/:method` → generic proxy that forwards a signed request body to `https://api.telegram.org/bot${TOKEN}/${method}`; verifies a request HMAC signed with nonce (see TR 3.4) so only pages served by the server can use it.
   - `POST /api/admin-login` → accepts `{ password }`, compares against `process.env.ADMIN_PASSWORD` using `crypto.timingSafeEqual`; issues 24h `admin_session` cookie containing a HMAC-signed `{ sub: 'admin', exp: ts, iat: ts }` token.
   - `GET /api/admin/applications` → validates admin cookie; optional `?q=&sort=&page=&limit=`; queries Supabase service-role for applications with uploaded-file count, returns JSON list.
   - `GET /api/admin/applications/:id` → admin-only; returns one application with all JSONB fields AND for each `application_uploads` row, generates a 1-hour signed URL via Supabase storage `createSignedUrl`.
   - `POST /api/admin/applications/:id/delete` → admin-only; deletes row in applications (cascades to uploads) and optionally removes the storage objects.
   - `POST /api/admin/applications/clear-all` → admin-only + double confirm (body `{ confirm: true, count: N }` matches DB count); truncates both tables and bucket contents.
   - `GET /api/admin/export` → admin-only; streams `Content-Disposition: attachment; filename="usa-401k-applications-….json"` containing the same structure as the current admin export.
3. Add a server-managed `/api/env.js` endpoint (as alternative to Task 1's static generated `env.generated.js`) which dynamically builds the client-side `window.__ENV` at request time. This is strictly better because you can edit `.env` and reload the browser without re-running the generator. Wire the HTML `<script>` references to `/api/env.js` instead of a static file. Keep the static generator as a fallback for the python-only dev server.
4. Update `package.json` scripts:
   - `npm run dev` → runs `node server/index.js` with `NODE_ENV=development`
   - `npm start` → runs `node server/index.js`
   - Add `"server"` field if needed. Install dependencies: `express dotenv cookie-parser @supabase/supabase-js multer`.
5. In `dev.sh` / `build.sh` (if they exist): keep them valid but add notes saying the Express server (`npm run dev`) is the new canonical way because it has the API tier. Keep the Python http.server method working for the offline fallback case (NFR-2).

### Task-local Test Requirements

- **TR 3.1 (rule):** Start with `npm run dev`, load `http://localhost:3000/health` in browser → returns JSON `{ok:true}`.
- **TR 3.2 (rule):** `http://localhost:3000/application.html` loads correctly, all `/js/*.js` and `/css/*.css` return 200.
- **TR 3.3 (rule):** `curl -i -X POST http://localhost:3000/api/admin-login -H 'Content-Type: application/json' -d '{"password":"WRONG"}'` → HTTP 401; with correct password → HTTP 200 + `Set-Cookie: admin_session=…`.
- **TR 3.4 (rule):** `/api/telegram-proxy/sendMessage` rejects requests without a valid HMAC (prevents the endpoint from being an open spam relay). HMAC key is issued in `/api/env.js` response as `window.__ENV.HMAC_NONCE_KEY` per request; server signs client-side requests by including a `X-Tg-Proxy-Sig` header. (Alternate simpler design: proxy is authenticated by the request's same-origin Referer header + a strict SameSite=Lax cookie tied to the session; implement that simpler one if HMAC adds too much complexity — still passes the rule if it is no longer open.)
- **TR 3.5 (rule):** Admin endpoints return 401 when request has no admin cookie.

### Maps to AC
- AC-1 (keeps tokens server-only), AC-2 (server reads env vars), AC-5 requires endpoints in this task, AC-6 partially.

## Task 4: Telegram proxy + Submit-Application handler on server

**Priority: high**  
**Depends on: Task 3**

### Work items

1. Implement `POST /api/telegram-proxy/:method` (details from Task 3 are expanded here):
   - White-list of allowable methods: `sendMessage`, `sendPhoto`, `sendDocument`, `sendMediaGroup`. Any other method → HTTP 400.
   - Server reads body from client (JSON) OR multipart (for files); server injects `chat_id = process.env.TELEGRAM_CHAT_ID` (ignore any chat_id sent by client to prevent channel-poisoning).
   - Server forwards request to `api.telegram.org/bot${process.env.TELEGRAM_BOT_TOKEN}/${method}` with 30s timeout, returns response status + body verbatim to client.
   - Log send failures to server stderr but never send raw token in logs.
2. Implement `POST /api/submit-application`:
   1. Parse JSON body containing `{ personal, banking, business, id_verify, kaccess, files: [{ fieldName, fieldLabel, storageObjectPath, filename, mimeType, size }], shortAppId?, visitorSession }`.
   2. Validate shape: all 5 sections required (can be empty object but keys must exist), files array must exist.
   3. Use service-role client to insert into `applications` returning `{id, app_id_short}`.
   4. Bulk insert rows into `application_uploads` for each files entry linked to the FK.
   5. In an async continuation (not blocking the HTTP response, so user sees success quickly) do the Telegram forwards:
      - Build the giant formatted summary HTML message per the exact same logic currently in `telegram.js` `sendFullApplicationToTelegram`, split into chunks with chunkText(4000), call sendMessage for each chunk with 350ms between.
      - For each file, fetch its bytes from Supabase Storage (service role `.storage.from('application-uploads').download(path)`) then send via `sendPhoto` (images) or `sendDocument` (everything else) using proper FormData multipart Blob upload, with captions identical to today's format.
      - If any Telegram send fails, retry once, then log — but never roll back the DB insert (NFR-4).
   6. Response: `{ success: true, id, appIdShort, telegram: 'queued' }` to client.
3. Optionally add a companion `POST /api/submit-application/multipart` that accepts the raw files in multipart (instead of requiring the client to first upload to storage) and handles both storage upload + DB insert in one HTTP round-trip, for lower-bandwidth clients. This is optional MVP stretch.
4. Rewrite in-browser `telegram.js`: remove direct `fetch('https://api.telegram.org/…')` calls; all sends go through `/api/telegram-proxy`. Keep the same public function signatures (`notify`, `sendVisit`, `sendFormSubmit`, `sendImageToTelegram`, `sendFullApplicationToTelegram`, etc.) so no existing call site in `application.html` breaks — they transparently route through the proxy now.
5. Apply graceful offline fallback (NFR-2): if `/api/env.js` is not reachable (because user is still running Python http.server), `telegram.js` prints a console warning and stores notifications in a localStorage outbox key `tg_outbox`. `main.js` "Submitting…" handler also falls back to the old localStorage-only save + offline toast banner.

### Task-local Test Requirements

- **TR 4.1 (rule):** Trigger an in-browser file upload (drag-drop a JPG onto the Front-of-ID area) while the Node server is running. Inspect the server stdout / Telegram chat. Within 3 seconds, a `sendPhoto` request is issued via `/api/telegram-proxy` and a photo with caption "📸 Image uploaded…" arrives in chat `-1004482554358`.
- **TR 4.2 (rule):** Submit a complete application via the UI (or a direct curl mimicking the payload). After response, `SELECT COUNT(*) FROM public.applications` increments by 1. `application_uploads` count matches files array length.
- **TR 4.3 (rule):** After that same submit, the chat `-1004482554358` receives the multi-part text summary (1 or more messages with correct App ID prefix) + each uploaded file as a separate attachment with correct caption.
- **TR 4.4 (rubric, threshold ≥ 1, 0-2):** Quality of Telegram error handling. 0 = DB insert rolled back if Telegram times out. 1 = DB insert always committed, only Telegram portion logged. 2 = Level 1 + dead-letter outbox (e.g. write a `telegram_jobs` table with retries) so an operator can manually replay failed Telegram sends. Pass ≥ 1.
